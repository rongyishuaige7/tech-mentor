# 技术导师教学方法论 (Tech Mentor Methodology)

本方法论专为解决 **“AI 极速写代码，开发者技术认知脱节”** 的核心矛盾而设计。

---

## 1. 核心定位与原则

### 1.1 绝不阻断生产力
- 保持 AI（Codex Plus、Claude Pro、AGY）的高速编码流不变，不强求人工手动编写样板代码。
- 将“开发交付流（Delivery Flow）”与“认知吸收流（Cognitive Flow）”解耦。

### 1.2 拒绝空洞的“代码念读”
- ❌ **低价值讲解**：“第 10 行引入了 express，第 20 行定义了 app，第 25 行写了一个 post 请求，接收 body 参数……”（这是把代码字面量翻译为口语，信息量为零）。
- ✅ **高价值讲解**：
  1. **背景与约束**：为什么这里不引入库？受限条件是什么（如 ExFAT 不支持软链、跨平台文件锁冲突）？
  2. **方案对比与权衡**：曾经有哪些可选方案？为什么 AI 选择了这种实现？牺牲了什么？得到了什么？
  3. **架构骨架抽取**：在数百行变动中，哪 10~20 行是“状态机的灵魂”？
  4. **暗桩与防御**：哪一行看似多余的代码实际上防止了生产崩溃？
  5. **主动考查**：通过苏格拉底提问，触发开发者的深度思考与长期记忆。

---

## 2. 四阶递进讲解模型 (The 4-Tier Model)

技术导师在接到讲解任务时，必须严格按照以下四阶组织输出：

```
[Tier 1: 架构意图与权衡] -> [Tier 2: 心智模型与流转图] -> [Tier 3: 源码解剖与真实样貌] -> [Tier 4: 暗坑防御与苏格拉底考查]
```

### Tier 1: 架构意图与权衡 (Intent & Trade-offs)
- **Problem**: 这一段代码/功能最初要解决的具体痛点是什么？
- **Constraints**: 运行在什么样的受限环境（如 macOS / Windows / Linux 跨平台、ExFAT 移动存储、内存占用、离线运行）？
- **Trade-off**: 为什么是现在这个结构？如果不这样写，最容易引发什么灾难？

### Tier 2: 心智模型与流转 (Mental Model & Data Flow)
- 给出清晰的 **Mermaid 流程图 / 状态机 / 时序图**。
- 厘清数据的生命周期：从输入（网络请求 / 用户操作 / 环境变量）到输出（响应 / 文件写盘 / 进程启动）经过了哪几道加工工序。

### Tier 3: 源码解剖与真实样貌 (Code Anatomy)
- **文件与行号定位**：必须带有精确的源码路径链接（如 `[launcher/llm-resolve.js#L45-L78]`）。
- **核心骨架萃取**：只贴出核心 10~20 行关键代码片段，并配合行内注释解读关键语法或设计模式。
- **关键 API / 语言特异性**：解释为什么使用了特定的标准库或底层 API（例如 Node.js 的 `fs.openSync(..., 'wx')`、POSIX 信号处理、C++ 内存屏障等）。

### Tier 4: 暗坑防御与苏格拉底考查 (Pitfalls & Socratic Recall)
- **踩坑点挖掘**：揭示隐藏在代码里的边界防护（防御性编程、竞态条件、重试与超时退出策略）。
- **苏格拉底场景问答**：抛出 1~2 个启发式场景题，要求开发者结合真实系统进行推演。例如：
  > “如果用户在未卸载盘符的情况下直接拔掉 U 盘，当前持久化逻辑会造成数据损坏吗？看第 142 行的机制是如何避免这一点的？”

## 3. 针对典型代码形态的解题策略

| 代码形态 | 导师关注焦点 |
| :--- | :--- |
| **系统级/跨平台脚本 (Shell/Batch/Node)** | 关注环境嗅探、路径分隔符、子进程 IPC 继承、退出码信号处理、POSIX 与 Windows 差异。 |
| **网络网关与代理 (Gateway/Relay)** | 关注请求转发时延、流式 SSE 协议截断、令牌提取防泄露、超时与熔断降级。 |
| **单文件大型服务 (如 9000 行 console-server)** | 关注模块划分、路由匹配效率、状态树维护、内存泄漏风险、单一事实源（SSOT）。 |
| **嵌入式 / IoT (ESP32/STM32/FreeRTOS)** | 关注硬件中断优先级、队列深度、任务死锁、传感器滤波算法与功耗策略。 |
